# Demo Day Preparation

How to present your hackathon project so judges understand the problem, see the solution, and remember your team.

---

## Slide Structure (5-7 slides, 5 minutes max)

### 1. Title (30 seconds)

- Project name
- One-liner: what does it do?
- Team name + members

### 2. The Problem (1 minute)

- Who has this problem?
- How bad is it? (quantify if possible)
- What's the current workaround?
- **Make the judges feel the pain**

### 3. The Solution (1 minute)

- What did you build?
- How does it solve the problem?
- What's the key insight or "aha moment"?

### 4. Live Demo (2 minutes)

- Show the core flow end-to-end
- Narrate as you go: "Here's what's happening..."
- Keep it smooth — don't click around randomly
- If something breaks, switch to backup immediately

### 5. How It Works (1 minute)

- Tech stack (keep it brief — judges don't need implementation details)
- Architecture diagram if relevant
- What's novel about your approach?

### 6. Impact + Future (1 minute)

- What would happen if this scaled?
- What would you build next?
- Business model or social impact

### 7. Thank You (30 seconds)

- Recap: problem → solution → impact
- "We're ready to take questions"

## Live Demo Tips

### Before the demo

- [ ] Test the full flow 3 times
- [ ] Use incognito browser (no cache issues)
- [ ] Pre-fill any data needed for the demo
- [ ] Have a backup video ready
- [ ] Test on the projector/screen if possible

### During the demo

- **Narrate everything** — don't click in silence
- **Slow down** — judges can't follow fast clicking
- **Start from a clean state** — fresh browser, logged out
- **Show the happy path first** — impress them before showing edge cases
- **Don't debug live** — if it breaks, switch to backup

### If the demo fails

| Failure | Recovery |
|---|---|
| API is down | Show pre-recorded video |
| Database error | Refresh and try again once, then switch to backup |
| Frontend won't load | Use the incognito test — it's usually a cache issue |
| Build fails | Show screenshots, explain what it does |
| Nothing works | Talk through the UX flow with screenshots |

**Rule**: Never debug on stage. The judges don't care about your debugging skills — they care about your product.

## Presentation Skills

### Do

- Make eye contact with judges
- Speak clearly and at a moderate pace
- Use concrete examples ("Imagine a nurse who...")
- Acknowledge limitations honestly
- Show enthusiasm — it's contagious

### Don't

- Read from slides
- Apologize for what you didn't build
- Use jargon without explanation
- Rush through the demo
- Argue with judges' feedback

## The 5-Minute Rehearsal

Practice this script:

> "Hi, we're [team name]. We built [project] to solve [problem].
>
> Currently, [pain point]. This costs [time/money/frustration].
>
> Our solution [does X]. Let me show you how it works.
>
> [DEMO]
>
> Under the hood, we used [tech stack]. The key insight was [novelty].
>
> If we had more time, we'd build [future features].
>
> Thanks — any questions?"

Time yourself. If it's over 5 minutes, cut something.

---

## Common Mistakes to Avoid

1. **Too much setup** — Get to the demo fast. Judges have short attention spans.
2. **Showing the code** — Judges care about the product, not your architecture.
3. **Apologizing** — Never say "we didn't have time to..." — say "next, we'd build..."
4. **No backup plan** — Always have screenshots or video ready.
5. **Running over time** — If the organizer says "wrap up," wrap up. Don't keep going.
